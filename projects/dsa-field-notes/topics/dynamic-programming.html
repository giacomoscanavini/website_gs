Dynamic programming

Define smaller subproblems, reuse their answers, and evaluate them in dependency order.

Start with the recurrence

Dynamic programming is useful when different choices lead to the same subproblem. A state must contain enough information to determine that subproblem's answer; otherwise two different situations may be incorrectly treated as the same one.

  1. State: write one sentence defining dp[state].
  2. Transition: express that answer using smaller states and the allowed choices.
  3. Base cases: give the smallest answers directly.
  4. Evaluation order: compute dependencies before using them.
  5. Final answer: identify the requested state, which is not always the last array entry.

Advantage: replaces repeated work with one computation per state. Limitations: a poor state definition gives wrong answers; too many states require too much time or memory. Recursion alone is not DP: reuse is what avoids repeated work.

A recurrence with two predecessors

Let f(i) count paths to step i using jumps of size 1 or 2. The final jump comes from i - 1 or i - 2. These cases do not overlap, so their counts add.

f(0) = 1   ·   f(1) = 1
f(i) = f(i − 1) + f(i − 2), for i ≥ 2

f(0) = 1 counts one empty path. For i = 2, the two paths are 1 + 1 and 2; thus f(2) = 2. Continue: f(3) = 3, f(4) = 5, f(5) = 8.

Direct recursion

The recurrence translates directly into code, but repeated calls compute the same answers again. For example, both f(4) and f(3) request f(2).

Python
# Time O(2^n): repeated calls, an exponential upper bound
# Extra space O(n): maximum recursion depth
def ways_recursive(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    if n <= 1:
        return 1
    return ways_recursive(n - 1) + ways_recursive(n - 2)

Top-down and memoization

Top-down starts from the requested state and recursively asks for its dependencies. Memoization saves a state's answer so later calls return it immediately. @cache uses the function arguments as the key.

Python
from functools import cache

# Time O(n): each state is computed once
# Extra space O(n): cached answers and recursion depth
def ways_top_down(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")

    @cache
    def solve(i: int) -> int:
        if i <= 1:
            return 1
        return solve(i - 1) + solve(i - 2)

    return solve(n)

The cache is local to each outer call. Every state from 0 through n is computed at most once, but the recursion can still be O(n) deep. Large n can exceed Python's recursion limit. A memoization key must include every changing input that affects the answer.

Bottom-up tabulation

Bottom-up starts with base cases and fills states in an order that respects their dependencies. Here dp[i] depends on smaller indices, so increase i from 2 to n.

Python
# Time O(n): fill n + 1 states once
# Extra space O(n): the table
def ways_bottom_up(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    if n <= 1:
        return 1
    dp = [0] * (n + 1)
    dp[0] = dp[1] = 1
    for i in range(2, n + 1):
        dp[i] = dp[i - 1] + dp[i - 2]
    return dp[n]

This avoids recursion overhead and recursion-depth limits, but computes every state in the chosen table. Keeping the table is useful when later queries or path reconstruction need older answers.

Optimize the stored state

Only the previous two values are needed for the next value. Before processing i, let older = f(i - 2) and previous = f(i - 1). Calculate current, then shift the two saved values forward.

Python
# Time O(n): one update per state
# Extra space O(1): a constant number of integer slots
def ways_rolling(n: int) -> int:
    if n < 0:
        raise ValueError("n must be nonnegative")
    older, previous = 1, 1
    for i in range(2, n + 1):
        current = older + previous
        older, previous = previous, current
    return previous

This uses a constant number of integer slots, but no longer retains the full history. Costs assume constant-time arithmetic on bounded-size values. Exact path counts grow with n; Python's arbitrary-precision integers make the arithmetic and bit storage grow too.

Common state patterns

Problem structure State and transition Typical cost
Count paths Add counts from disjoint predecessor cases Number of states × choices per state
Minimum cost Take the minimum of predecessor cost + current cost Number of states × choices per state
Choose or skip Compare the answer with and without an item Often O(nC) for capacity C
Grid paths dp[r][c] = dp[r-1][c] + dp[r][c-1], with valid boundaries O(rows × columns)
Two sequences dp[i][j] describes their prefixes Often O(nm)

For longest common subsequence, dp[i][j] is the best length in the first i and j elements. If the last elements match, use 1 + dp[i-1][j-1]; otherwise use max(dp[i-1][j], dp[i][j-1]). Empty prefixes have value zero.

Minimize: the final coin

Let dp[total] be the fewest coins needed to make exactly total. For every coin that fits, try one coin plus the best answer for the remainder. Denominations may be reused.

dp[0] = 0
dp[t] = min(1 + dp[t − coin]) over coins ≤ t
Python
# Time O(A * c): A is the amount, c is the number of denominations
# Extra space O(A): one entry per subtotal
def min_coins(coins: list[int], amount: int) -> int:
    if amount < 0 or any(coin <= 0 for coin in coins):
        raise ValueError("Use a nonnegative amount and positive coins")
    dp = [amount + 1] * (amount + 1)
    dp[0] = 0
    for total in range(1, amount + 1):
        for coin in coins:
            if coin <= total:
                dp[total] = min(dp[total], 1 + dp[total - coin])
    return -1 if dp[amount] > amount else dp[amount]

The unreachable sentinel is amount + 1: positive integer denominations cannot require more than amount coins for a feasible solution. An amount of zero returns zero; an unreachable positive amount returns -1. The algorithm is pseudo-polynomial: its cost depends on the numeric amount, not only on the digits needed to represent it.

Choose or skip: one item at most once

For 0/1 knapsack, let D(i, cap) be the best value using the first i items within capacity cap. Skip the new item, or take it and use the preceding item row at the remaining capacity.

D(i, cap) = max(D(i − 1, cap), value + D(i − 1, cap − weight))

The take branch exists only when the item fits. Compressing rows into one array requires capacities to run backward, so dp[cap - weight] still describes the previous item row.

Python
# Time O(n * C): n items and capacity C
# Extra space O(C): keep only one row
def knapsack(weights: list[int], values: list[int], capacity: int) -> int:
    if len(weights) != len(values) or capacity < 0:
        raise ValueError("Check lengths and capacity")
    if any(weight <= 0 for weight in weights):
        raise ValueError("Weights must be positive integers")
    dp = [0] * (capacity + 1)
    for weight, value in zip(weights, values):
        for cap in range(capacity, weight - 1, -1):
            dp[cap] = max(dp[cap], dp[cap - weight] + value)
    return dp[capacity]

Backward capacity: each item can be used once. Forward capacity: newly updated entries can reuse the same item, giving the unbounded variant. For weight 2, value 3, and capacity 4, a forward pass can incorrectly use that single item twice and report 6.

Compare the approaches

Approach Strength Cost or limitation
Direct recursion Closely follows the recurrence May recompute states exponentially often
Top-down + memoization Computes only reached states Cache memory and recursive call stack
Bottom-up table Explicit order, no recursive calls Stores a table and may fill unused states
Rolling state Keeps only live dependencies Usually loses easy reconstruction of earlier choices

For a grid stored in one row, an old dp[c] can mean "above" while updated dp[c-1] means "left". For a recurrence that also needs the old diagonal, save it before overwriting. Space optimization is safe only after checking which version of each state is required.

Reading the complexity comments

n is the input length unless another size is defined. Extra space excludes the input and counts stored results when they are constructed. Recursion frames count as extra space. Costs assume bounded-size values and constant-time comparisons; dictionary and set costs are expected under ordinary hashing. The step viewer stores snapshots for illustration; that storage is not part of the displayed algorithm.
